# ADR NNNN — Concise Decision Title

- **Status:** Proposed | Accepted | Superseded | Rejected
- **Date:** YYYY-MM-DD
- **Owner / reviewers:** TBD
- **Related requirements:** TS-...
- **Related issues / PRs:** links
- **Supersedes / superseded by:** links or none

## Context and observed facts

Describe the user need, environmental constraints, current implementation state, standards and evidence. Distinguish verified observations from assumptions.

## Decision drivers

State non-negotiable product/security/localization/testing requirements and measurable criteria.

## Options considered

Describe each plausible option with evidence, licensing, maintenance, compatibility, performance, privacy, complexity and rollback implications.

## Decision

State the selected option and why. **Do not mark Accepted until the project owner or designated maintainers explicitly agree.** An accepted ADR describes intent; it is not proof of implementation.

## Consequences and boundaries

List required changes, affected interfaces, user data, dependencies, permission and network implications, migrations, failure cases and known limitations.

## Acceptance and verification plan

Link exact requirements, test fixtures, expected behavior, target platforms, and actual results (initially NOT_RUN). Explain how success is demonstrated.

## Rollback / evolution strategy

Specify what remains replaceable, how migration or rollback works, and what would justify reconsideration.

## References and change history

Use stable relative links, external standards and dated revisions. If superseding a decision, retain the old ADR for the record.
